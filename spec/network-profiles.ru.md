## 0. Цель

На одной машине одновременно работают несколько нативных агентских сред. Каждый запуск должен выходить в сеть через собственный прокси уровня приложения, не меняя оркестратор, соседних агентов и операционную систему:

```text
codex A  ─► proxy :18081 ─► VPN / upstream A
claude B ─► proxy :18082 ─► VPN / upstream B
pi C     ─► proxy :18081 ─► VPN / upstream A
orchestrator and everything else ─► the machine's ordinary network
```

Запуск сохраняет своё окружение, учётные данные, привязку среды выполнения, модель и рабочий каталог; сетевой профиль меняет только то, как устанавливаются поддерживаемые соединения. Первый релиз — это **кооперативная маршрутизация поддерживаемых клиентов через прокси**, а не принудительная изоляция дерева процессов. Поэтому он называется *сетевыми профилями* и никогда *сетевой песочницей*. Будущая принудительная песочница использует тот же профиль как описание своего выхода в сеть.

## 1. Факты платформы (проверены, если не помечено иное)

| Факт | Где |
| --- | --- |
| Есть три владельца процессов, и каждый запускает процессы агентских сред из значений, которые сам собирает: `curator-run` (интерактивные запуски), `internal/spawn` в task-board (отслеживаемые дочерние агенты), the session host (основные сессии доски, хост app-server для codex, PTY для claude) | LP §3.3, LP-D5, LP-D6 |
| `curator-run` собирает argv плана → флаги промпта → флаги MCP → нативный хвост и применяет четыре слоя окружения; его отслеживаемый транспорт несёт только собственные литералы, `env_names`, `argv_suffix` и stdin | README лаунчера, раздел «Environment and transport»; SPEC 0.4.0-draft §4.5–4.6 |
| Плагины модуля фильтруют окружение дочернего процесса: codex удаляет одиннадцать конкретных ключей (`CODEX_*`, указатели на эндпоинты task-board) и чистит `PATH`; claude удаляет только `CLAUDECODE`; pi передаёт окружение родителя как есть | модуль: `internal/runtimeenv`, `systems/claude/env.go`, `systems/pi/env.go` |
| Запрос плана запуска в ax: `env_literals` (значения) и `env_names` (поиск по имени на стороне получателя); имя, которое есть и среди литералов, выбрасывается из списка разрешённых с предупреждением | спецификация ax §14.1; curator-spec Decision 0013 D6.3 |
| Claude Code документирует `HTTP_PROXY`/`HTTPS_PROXY` (и `NO_PROXY`) и не поддерживает SOCKS; фоновых агентов обслуживает общий супервизор на пользователя, который может сохранить окружение первой оболочки, запустившей его | документация Claude Code (для детали про супервизор — docs-confidence) |
| OpenCode документирует переменные прокси и то, что прокси нужно обходить для его локального TUI-сервера | документация opencode (docs-confidence) |
| Websocket-дозвонщик Codex понимает стандартные переменные прокси и маршруты прокси | чтение исходников codex (для установленной сборки — docs-confidence) |
| `curl` читает только `http_proxy` в нижнем регистре; `NO_PROXY=*` отключает прокси; клиенты расходятся в регистре и приоритете | документация curl |
| Локальные движки под `curator-inference-manager` слушают loopback; у direct нет прокси и нечего обходить, поэтому проверка покрытия хостов движков к нему не применяется. Профили движков в режиме SSH подключаются к удалённым машинам по собственному каналу | LP-D7, LP-D8; `model-harness` в agents-infra, `mode = local\|ssh` |

## 2. Решения

### N1 Пять независимых настроек запуска

| Настройка | Что решает | Владелец |
| --- | --- | --- |
| Профиль окружения (Curator) | контекст, домашний каталог, скиллы, MCP, граница учётной записи | Curator |
| Выбор учётных данных | какой вход использует домашний каталог (`shared`/`isolated`) | Curator |
| Привязка среды выполнения (LP-D1) | какая агентская среда к какому провайдеру или движку ходит | конфигурация task-board + каталог модуля |
| **Сетевой профиль** | через какой прокси уровня приложения идут поддерживаемые соединения | `curator-network-profiles` + владелец процесса |
| Профиль исполнения | где и в каких пределах работают инструменты | среда исполнения |

Сетевой модуль никогда не копирует логины, не меняет домашние каталоги провайдеров, не выбирает учётную запись и не сбрасывает учёт квот; другой маршрут никогда не становится новым доменом квоты. Словарь CLI следует форме командной строки от 2026-09-27, которая заменяет словарь LP-D12: `--runtime <id>` (псевдоним `--agent`) для привязки, `--profile <name>` для профиля Curator и в task-board, и в `curator run`, а **`--network <name>`** для сетевого профиля. Слово `profile` без уточнения означает только профиль Curator; сетевой профиль никогда не выбирается через `--profile`.

### N2 Одна библиотека, три владельца процессов

Go-модуль **`curator-network-profiles`** (имя решено 24.09.2026): `resolve → validate → conditional probe → patch` (direct и планы/сухие запуски пропускают все пробы). Он не импортирует ни task-board, ни `curator-model-router`, ни хранилище ax: это его вызывающие. Он не создаёт процессов и не владеет демоном.

Каждый владелец процесса применяет привязку непосредственно перед запуском на каждом своём пути создания процессов: `curator-run` (интерактивные запуски), `internal/spawn` в task-board (дочерние агенты, повторы, рекурсивные запуски рабочих, возобновление), the session host (основные сессии, включая хост app-server для codex и PTY-хост для claude, при запуске и при возобновлении). `curator-inference-manager` — четвёртый владелец процессов, только его процессы — движки, а не агентские среды: сетевая часть движков вне этого эпика (N12).

### N3 Модель данных

`NetworkSelection` (что попросил вызывающий): `profile_ref`, `origin ∈ {explicit, inherited, runtime-default, profile-binding, project-default, operator-default}`, `required_assurance ∈ {cooperative, enforced}`.

`inherited` означает, что владелец процесса передаёт разрешённую ссылку родителя, сохранённую при резервировании, для повторного разрешения на хосте ребёнка; библиотека никогда не извлекает её из окружения или значений прокси.

`NetworkProfile` (что есть на машине) хранится в файле оператора `~/.curator/network.toml`: для каждой плоскости — один машинный каталог, рядом с остальными файлами оператора в `~/.curator/`; лаунчер и task-board никогда не держат двух копий. Его предлагали как `$XDG_CONFIG_HOME/curator-network-profiles/network.json`; curator-playbook `spec/process-configuration.md` §2.3 перенёс его; выбран TOML, потому что люди редактируют файл вручную. Имя таблицы `networks` — *предложено*: слово `profile` обозначает только профиль Curator.

```toml
schema = "relux-network-profiles-v1"

[networks.egress-a]
kind         = "external-http-proxy"
endpoint     = "http://127.0.0.1:18081"
bypass_hosts = ["localhost", "127.0.0.1", "::1"]

[networks.egress-b]
kind         = "external-http-proxy"
endpoint     = "http://127.0.0.1:18082"
bypass_hosts = ["localhost", "127.0.0.1", "::1"]
```

Виды профилей: `external-http-proxy` и `direct`. Именованный профиль `kind = "direct"` не содержит `endpoint`, `bypass_hosts` или `probe_target`; эти ключи ОБЯЗАНЫ отклоняться при наличии, даже если они пусты.

```toml
[networks.direct]
kind = "direct"
```

Файл редактируют через `curator network add|remove` или вручную. Добавление или изменение любого сетевого профиля, включая direct, — запись, расширяющая разрешения, потому что оно меняет маршрут трафика: оно вступает в силу только после `curator network confirm`, а эта команда отказывается выполняться в агентской сессии (relux-works/curator-trust `spec/trust.md` §10).

`NetworkBinding` (что применяется): `profile_ref`, `profile_digest`, `adapter_identity` (сборка агентской среды + точка входа + плагин), `resolved_endpoint`, `assurance`, `env_patch`; позже `lease_id` и `generation` для управляемого шлюза. Манифесты запусков хранят `profile_ref`, `profile_digest`, `adapter_identity`, `assurance` и результат пробы; полное окружение и адрес с учётными данными туда никогда не попадают. Дайджест фиксирует конфигурацию, а не фактический выход внешнего прокси в сеть.

`env_patch` — это две упорядоченные операции, сначала `unset`, потом `set`. `unset` удаляет из окружения хоста, который создаёт процесс, все известные адаптеру переменные семейства прокси в обоих написаниях, а `set` записывает согласованный набор прокси из N5 (пустой для direct); патч никогда не состоит из одних добавлений. `profile_digest` считается по нормализованному итоговому профилю (версия схемы, вид, эндпоинт, отсортированные `bypass_hosts`, *режим* учётных данных без секретов; для direct — только версия схемы, вид и режим учётных данных) и никогда по результатам проб, идентификаторам аренд или временным меткам. Две привязки **равны**, когда равны `profile_digest`, `adapter_identity` и `assurance`; совпадение имени профиля ничего не доказывает.

Запись в `runtimes.toml` (LP-D2) МОЖЕТ нести `network = "<name>"` как значение по умолчанию для этой привязки, а конфигурация проекта МОЖЕТ нести `spawn.network.default = "<name>"` (решено 2026-09-22 после ревью). Оба значения — стабильные идентификаторы профилей: их разрешают на каждой машине, а там, где такого профиля нет, следует отказ `network_profile_unknown`. Явный `--network` важнее обоих.

Привязки профилей берутся только из `[bindings.profiles]` в каталоге оператора
на хосте назначения (`~/.curator/network.toml`), по точному имени
`resolve.Request.CuratorProfile`. Файлы проекта, профиля Curator и переменные
окружения не служат источником привязок. Нормативные правила:
[приложение §3.7](contract-appendix.md#37-selection-and-inheritance-spec-n3-n4-n8).

### N4 Приоритет и уровень гарантии

Блокировки хоста и набор разрешённых профилей → явный выбор → унаследованный выбор → значение по умолчанию привязки среды выполнения → привязка профиля оператора (`profile-binding`) → значение по умолчанию проекта → значение по умолчанию оператора (собственная запись машины со значением по умолчанию в `network.toml`). Если не выбрано ничего, поведение остаётся сегодняшним и сообщается как `unmanaged`, а не как «прямое». Явный выбор именованного direct — управляемый запуск: он проходит проверку набора разрешённых профилей и подтверждения, а в запись попадают его `profile_ref` и дайджест. Запрос `enforced` на машине, где есть только кооперативный бэкенд, отклоняется; первый релиз публикует `assurance = cooperative`.

### N5 Применение патча без побочных эффектов

Патч попадает только в приватное окружение дочернего процесса. Никогда не `os.Setenv`, не профили оболочки, не системный прокси, не общее окружение tmux и не переписывание пользовательского `settings.json`. Порядок: убрать все конфликтующие унаследованные переменные прокси, затем выставить согласованный набор:

```text
HTTP_PROXY=<endpoint>   HTTPS_PROXY=<endpoint>
http_proxy=<endpoint>   https_proxy=<endpoint>
NO_PROXY=<bypass list>  no_proxy=<bypass list>
```

Для `direct` патч содержит **только unset**: то же семейство прокси удаляется без учёта регистра, а set пуст. Ребёнок direct не видит унаследованных переменных прокси; unmanaged сохраняет текущее окружение.

`ALL_PROXY`, переменные для websocket и настройки среды выполнения добавляет только адаптер агентской среды в модуле, и только после проверки; никто не выставляет десяток переменных на веру. Если нативные настройки инструмента перекрывают окружение, адаптер применяет поддерживаемое переопределение на один запуск или отказывает с `network_configuration_conflict`; общую конфигурацию он никогда не переписывает. Переменные прокси — это **собственные литералы** владельца процесса, ровно как `ANTHROPIC_BASE_URL` в транспорте `env-bundle` для claude (LP-D3); в документе ax они едут как `env_literals`, никогда как `env_names`. Собственная подготовка Curator (`curator env resolve`, установка, починка) по умолчанию через прокси не идёт; проксирование подготовки — отдельное явное требование.

### N6 Форма шлюза

Общая поверхность — **HTTP-прокси с CONNECT**, потому что Claude Code поддерживает переменные HTTP/HTTPS-прокси и не поддерживает SOCKS. За ней может стоять вышестоящий HTTP-прокси, SOCKS или конечная точка WireGuard. Первый кандидат на управляемый бэкенд — sing-box со слушателем `mixed` на loopback, `set_system_proxy: false`, без TUN, с WireGuard без системного интерфейса и закреплённой поддерживаемой версией. На этапе A шлюз настраивает оператор: библиотека только читает профиль и проверяет эндпоинты прокси пробой (для direct пробы пропускаются), а запускает владелец процесса или `curator network exec`. Это сетевой туннель, а не LLM-шлюз: API моделей, промпты, идентификаторы моделей и учётные данные не трогаются; проверка TLS остаётся включённой; корпоративная инспекция TLS — отдельный явный режим.

### N7 Поддержка агентских сред зависит от формы запуска

Поддержка проверяется для кортежа `harness build + entrypoint + adapter + configuration profile`, а не для «claude вообще». MVP поддерживает **свежий процесс агентской среды на каждый запуск**. Подключиться к уже работающему app-server или демону можно, только если его привязка равна запрошенной или адаптер умеет задать маршрут на уровне сессии; иначе `network_scope_unsupported`. Claude `--bg` через общий супервизор явно не поддерживается. the session host проверяет равенство привязок своих хостов при запуске и при возобновлении. Различаются два события: **новое назначение** на уже работающий хост и **повторное подключение или возобновление** существующего запуска. Переходы зафиксированы:

| Событие | Ситуация | Итог |
| --- | --- | --- |
| новый запуск | свежий процесс | разрешить, привязать, запустить |
| новое назначение на работающий хост | привязка хоста равна (N3) разрешённой | подключиться |
| новое назначение на работающий хост | привязка отличается, адаптер умеет маршрут на уровне сессии | задать маршрут для сессии, записать привязку |
| новое назначение на работающий хост | привязка отличается, маршрута на уровне сессии нет | отказ `network_scope_unsupported` |
| повторное подключение или возобновление существующего запуска | записанная привязка равна свежему разрешению | подключиться заново / возобновить |
| повторное подключение или возобновление существующего запуска | то же имя профиля, другой дайджест | отказ `network_profile_drift`; перемаршрутизация на уровне сессии не обходной путь; оператор восстанавливает профиль или начинает новый запуск |
| повторное подключение или возобновление существующего запуска | профиль отсутствует или запрещён | `network_profile_unknown` / `network_profile_denied` |

Операции «сменить сетевой профиль» на уровне сессии в MVP нет; она появится вместе с поколениями шлюза (N14). Новые пути агентских сред попадают в матрицу по мере появления: exec-режим `pi-native` (LP-D8) и плагин opencode (LP-D3); матрица перепрогоняется на каждом закреплённом релизе инструмента.

### N8 Точки интеграции

- `curator run <runtime> --profile <p> --network egress-a -- <args>`: разрешить, проверить совместимость, сделать ограниченную по времени предварительную проверку только для профилей прокси, наложить патч после обычной сборки окружения; допуск и поздние проверки не меняются.
- `task-board spawn … --network egress-a`, а также `spawn.network.default` и `network` у привязки: оркестратор выбирает идентификатор профиля из разрешённого набора и никогда не передаёт сырой адрес прокси. Дочерний агент наследует профиль **по ссылке с повторным разрешением**, с `origin = inherited`, а не копированием окружения оркестратора; родитель на A может запустить ребёнка на B.
- Манифесты: рядом с `RuntimeProvenance` и `profile.name`/`lock_sha256` из Curator (LP-D11) — `network.profile_ref`, `profile_digest`, `adapter_identity`, `assurance`.

### N9 Отслеживаемые сессии (ax)

Отслеживаемый транспорт сериализует только собственные литералы, поэтому прокси, выставленного на самом внешнем процессе, недостаточно для надёжного возобновления. Ссылка на сеть и дайджест едут в версионированном контракте. Фактический хост процесса разрешает привязку непосредственно перед запуском или возобновлением и заново собирает из неё окружение дочернего процесса. Половина `unset` патча выполняется против собственного унаследованного окружения хоста, так что конфликтующая переменная, которая есть только на хосте, удаляется там; литералы, которые несёт транспорт, — это только половина `set`. Пока этого нет, отслеживаемый режим с обязательным сетевым профилем отказывает; прямой режим выходит независимо.

### N10 Жизненный цикл, проверки, ошибки

`resolve → validate profile + adapter → conditional bounded proxy preflight → prepare binding → spawn → record outcome`. Direct и планы/сухие запуски пропускают предварительную проверку; их поля tcp/connect/tls в `ProbeRecord` равны `skipped`. На этапе A нет ни планировщика, ни регистрации демона, ни модели аренд. `curator network show` и план только читают; `curator network check` проверяет без сетевого вызова, а `check --probe` для профилей прокси — явный сетевой вызов (предложенный `netrun doctor`); предварительная проверка запуска ограничена по времени и не использует учётные данные моделей. Три разных факта: открытый TCP-порт; успешный CONNECT и TLS до согласованной цели; внешний IP, увиденный только для этой проверки. Коды сбоев: `network_profile_unknown`, `network_profile_denied`, `network_scope_unsupported`, `network_configuration_conflict`, `network_proxy_unreachable`, `network_proxy_auth_failed`, `network_profile_drift`. Если профиль отсутствует, запрещён, не поддерживается или недоступен, агент не запускается: скрытого перехода на прямое соединение нет, автоматического переключения VPN или учётной записи тоже; отказ запуститься — это не аварийный выключатель ОС. О разрыве посреди запуска сообщается владельцу запуска, и решает он; ничто не перезапускает задачу безусловно.

Для direct предварительная проверка и `check --probe` пропускают все три шага (`tcp`, `connect`, `tls` = `skipped`); подключений к эндпоинту нет.

### N11 Граница покрытия и секреты

Direct тоже кооперативный: удаление переменных прокси не гарантирует прямой маршрут на уровне ОС.

Профиль действует на поддерживаемые сетевые клиенты агентской среды, а это может быть не только инференс, но и обновление авторизации, HTTP MCP и другие запросы. Дочерние команды могут унаследовать переменные, но подчиняются ли они им, зависит от клиента, а не гарантируется ОС. Вспомогательный процесс, который запускает агентская среда (stdio MCP-сервер, мост инструментов), наследует патч, как любой дочерний процесс. Если такому процессу нужно ходить к управляющей плоскости своим маршрутом, его исходящий клиент настраивается явно и никогда не берётся из унаследованных переменных прокси. Так выход агентской среды в сеть и транспорт моста проверяются вместе, а упавший прокси инференса никогда не роняет управляющий канал. Вне гарантии: отдельно открытый браузер для OAuth, уже работающие сервисы, сырые сокеты и UDP, инструменты, выполняемые на удалённом EnvironmentHost. Пароли вышестоящих прокси и ключи WireGuard живут в шлюзе; агент получает эндпоинт на loopback. Слушатель на loopback без аутентификации клиента не изолирует локальные процессы друг от друга. В логи пишутся запуск и попытка, идентификатор профиля, дайджест, адаптер и сборка, результат пробы; сырое окружение, токены, `Authorization`, `Proxy-Authorization` и тела запросов не пишутся никогда.

### N12 Движки

Локальные эндпоинты `curator-inference-manager` находятся на loopback и ОБЯЗАНЫ стоять в `bypass_hosts` каждого прокси-профиля, иначе агентская среда пойдёт к своей локальной модели через прокси. У direct нет прокси, поэтому нечего обходить и проверка покрытия хостов движков не применяется. Профили движков в режиме SSH подключаются через собственный канал провайдера движков, и переменные прокси агентской среды их не касаются. Будущая принудительная песочница считает движок на loopback локальным сервисом, который нужно разрешить явно, а не «интернетом».

### N13 Роутинг

`curator-model-router` решает, что запускать; `curator-network-profiles` решает, через какой разрешённый маршрут это подключается. Роутер может учитывать совместимость с обязательным сетевым профилем как ограничение и никогда не переключает VPN, учётные данные или домены квот. Привязка среды выполнения, у которой в каталоге по умолчанию стоит другой профиль, — это не переключение маршрута роутером. До подсчёта оценок `CandidateResolver` вызывающего разрешает зависимые настройки каждого кандидата (сетевой профиль, профиль Curator, домашний каталог) по приоритету N4. Явно запрошенный профиль он фиксирует для всех кандидатов и исключает кандидата, у которого разрешённое значение отличается от зафиксированного, если только маска свободных полей политики роутинга не освобождает этот член (спецификация роутинга, R7). Это разрешение — поиск по данным, а не проба прокси; предварительная проверка N10 остаётся отдельным шагом запуска. Сбой сети — не свидетельство о качестве модели и никогда не снижает её оценку в кодинге. У бэкенда-оценщика свои явно назначенные учётные данные, выход в сеть и политика данных.

### N14 Будущее: управляемый шлюз

Добавляет `acquire / inspect / release`. Аренда принадлежит владельцу фактической среды выполнения, а не короткоживущему лаунчеру, который передал сессию дальше; завершение одного агента не должно останавливать прокси для остальных; изменение конфигурации создаёт новое поколение шлюза и никогда молча не переносит активные сессии. Принудительная песочница исполнения — отдельный эпик, и она использует профиль как описание своего выхода в сеть.

## 3. Этапы и приёмка

| Этап | Что даёт | Ценность |
| --- | --- | --- |
| A. Общий механизм | схема и файл профилей, резолвер, `EnvPatch`, бэкенд внешнего HTTP-прокси и провайдер Curator `curator-network`: `curator network exec <name> -- <cmd>`, `check [--probe]`, `list`, `show`, `add`, `remove`, `confirm` (заменяют предложенные `netrun --profile X -- <cmd>` и `netrun doctor X`) | независимые ручные запуски без глобального `export` |
| B. Лаунчер | `curator run --network`, проверенные точки входа, манифесты | окружение и сеть в одном запуске |
| C1. Оркестрация, явный профиль | `internal/spawn` в task-board и the session host на каждом реальном пути создания процессов (запуск, повтор, возобновление, рекурсивные дети) с явным `--network`, метаданные запуска | оркестратор запускает локальных субагентов через разные выходы в сеть |
| C2. Оркестрация, значения по умолчанию | значения по умолчанию из `runtimes.toml` для каждой привязки, значение по умолчанию проекта, их происхождение `origin` | значения по умолчанию без флага на каждом запуске |
| D. Управляемый шлюз | необязательный бэкенд sing-box, аренды во владении среды выполнения, поколения | автоматическое развёртывание прокси и WireGuard |
| Отдельный эпик | принудительная песочница исполнения | защита от обхода и изоляция |

A не ждёт D; C не ждёт ни удалённого пула, ни собственной агентской среды, ни распределённого журнала. C1 ждёт фазу 0 LP только там, где the session host сам собирает свои планы (патч должен попасть в этого сборщика); C2 ждёт фазу 1 LP (появление каталога). Приложение с контрактом из §5 входит в результаты этапа A.

Приёмка:

| Проверка | Ожидание |
| --- | --- |
| Параллельность | два процесса одной агентской среды одновременно используют два выхода в сеть, не трогая ни родителя, ни соседей |
| Композиция | конфликты нижнего и верхнего регистра и унаследованный `NO_PROXY=*` никогда не перекрывают явный профиль |
| Совместимость | настоящий HTTPS, стриминг, используемый websocket и подключения к локальным сервисам проверены для каждой точки входа на закреплённых версиях |
| Отказ | неизвестный, запрещённый, недоступный или неподдерживаемый профиль приводит к отказу до запуска; скрытого перехода на прямое соединение нет |
| Оркестрация | привязка применяется в самом дочернем процессе, включая заявленные пути повтора и возобновления |
| Учётные данные | модуль не меняет учётную запись и не пропускает ни одного секрета в конфигурацию, манифесты или логи |
| Совместимость с существующими запусками | запуски без выбора ведут себя как раньше; допуск и терминальный жизненный цикл не обходятся |
| Честный уровень гарантии | публикуется `assurance = cooperative`; запрос `enforced` не может получить кооперативный запуск |
| Движки | эндпоинты движков на loopback есть в списке обхода каждого профиля |
| `unset` на границе | конфликтующей переменной прокси, которая есть только на хосте, создающем ребёнка, в окружении ребёнка нет |
| Равенство привязок | повторное подключение или возобновление существующего запуска, у которого под тем же именем изменилось содержимое профиля, отклоняется с `network_profile_drift` и никогда не перемаршрутизируется на уровне сессии; новое назначение на работающий хост с другой привязкой даёт `network_scope_unsupported`, если адаптер не умеет маршрут на уровне сессии |

## 4. Правила и не-цели

- Никогда `os.Setenv`, никогда смена системного прокси, никогда переписывание общей конфигурации; патч живёт в окружении дочернего процесса.
- Никогда сырой адрес прокси от оркестратора; только идентификаторы профилей из разрешённого набора.
- Никогда скрытый переход на прямое соединение, на другой VPN или на другую учётную запись.
- Никогда переменные прокси как `env_names`; это собственные литералы.
- Это не LLM-шлюз, не песочница, не оркестратор VPN и не второй супервизор процессов.

## 5. Приложение с контрактом (результат этапа A)

Короткое приложение с тестовыми векторами, написанное вместе с кодом, фиксирует то, что этот документ только называет:

| Область | Что определяет |
| --- | --- |
| Дайджест профиля | нормализованное содержимое (N3), канонический JSON с отсортированными ключами и явной версией схемы, SHA-256 по этим байтам |
| `EnvPatch` | точный набор `unset` и набор `set` для каждого адаптера, оба написания, `ALL_PROXY` и переменные websocket только там, где проверены |
| Равенство привязок | список членов (N3) и то, что исключено: время пробы, аренда, поколение |
| Векторы | конфликты регистра, унаследованный `NO_PROXY=*`, конфликтующая переменная только на хосте, изменённое содержимое под неизменным именем, движок на loopback в списке обхода и вне его |
